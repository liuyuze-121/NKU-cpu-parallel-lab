\section{实验任务简述}

单条 query 在 GPU 上难以充分利用硬件并行度，通常需要将多个 query 组成 batch 共同处理。有两个主要方向为：第一，将内积距离计算转换为矩阵乘法形式；第二，在 IVF 上进行查询间并行，并分析 batch 内不同 query 的候选簇不一致带来的浪费。

本实验围绕这两个要求实现并测试三类 GPU 算法：
\begin{enumerate}
  \item \textbf{GPU Flat Batch Matrix Baseline}：将 base 向量矩阵与 query batch 相乘，生成完整距离矩阵，再选取每列 Top-$k$。
  \item \textbf{GPU IVF Cluster-Union Matrix Baseline}：对 batch 内 query 选择的 IVF 簇取并集，以簇为单位做“簇矩阵 $\times$ query batch”的距离计算，作为 IVF 方向的矩阵 baseline。
  \item \textbf{GPU IVF Compact Pair Optimization}：针对 IVF batch 中簇选择不同导致的无效计算，将有效的 $(query,candidate)$ 对压平成一维任务，只计算真正需要的候选距离。
\end{enumerate}

\section{算法设计}

\subsection{GPU Flat Batch Matrix Baseline}

\subsubsection{原理}

设 base data 为矩阵 $B\in\mathbb{R}^{N\times d}$，query batch 为 $Q\in\mathbb{R}^{m\times d}$。内积相似度矩阵可写为：
\[
  S = BQ^\top,\qquad S_{i,t}=\ip{x_i}{q_t}.
\]
距离矩阵为 $D_{i,t}=1-S_{i,t}$。在实现中，为了避免在没有 cuBLAS 的环境中引入额外依赖，baseline 使用手写 kernel：每个 CUDA thread 计算一个 $(query,base)$ 对应的内积。该方法保留了矩阵乘法 baseline 的核心任务划分，即将多个 query 合并成 batch，让 GPU 同时处理 $mN$ 个距离项。

\subsubsection{伪代码}

\begin{breakablealgorithm}
\caption{GPU Flat Batch Matrix Baseline}
\begin{algorithmic}[1]
\Require base 矩阵 $B$，query 集合 $Q$，batch 大小 $m$，近邻数 $k$
\Ensure 每条 query 的 Top-$k$ 结果
\State 将 $B$ 上传到 GPU
\For{每个 query batch $Q_b$}
  \State 将 $Q_b$ 上传到 GPU
  \State 启动 $|Q_b|\times N$ 个 GPU 线程
  \ForAll{线程 $(t,i)$ \textbf{in parallel}}
    \State $D[t,i]\gets 1-\sum_{j=1}^{d} B[i,j]Q_b[t,j]$
  \EndFor
  \State 将 $D$ 拷回主机
  \For{batch 内每条 query $t$}
    \State 对 $D[t,:]$ 执行 Top-$k$ 选择
  \EndFor
\EndFor
\end{algorithmic}
\end{breakablealgorithm}

\subsubsection{复杂度}

对一个 batch，GPU 距离打分需要计算 $mN$ 个内积，每个内积长度为 $d$，因此算术复杂度为 $\bigO{mNd}$。距离矩阵需要保存 $mN$ 个浮点数，显存输出空间与设备到主机传输量均为 $\bigO{mN}$。主机侧使用大小为 $k$ 的最大堆维护每条 query 的 Top-$k$，选择复杂度为 $\bigO{mN\log k}$，额外空间为 $\bigO{mk}$。该算法不包含索引构建阶段。

\subsubsection{算法分析}

Flat Batch 是 GPU ANN 实验中的精确基线：它不牺牲召回率，能够直接衡量 GPU 对批量内积距离计算的加速能力。算法的并行粒度是单个 $(query,base)$ 距离项，任务划分规则、负载均衡稳定，适合验证 batch size 对 kernel launch 开销、显存带宽和 PCIe 传输的影响。其主要局限在于必须生成并回传完整 $m\times N$ 距离矩阵，后续 Top-$k$ 仍在 CPU 侧完成；因此当 $N$ 和 $m$ 较大时，端到端性能会受到结果写回与主机选择阶段约束。

\subsection{GPU IVF Cluster-Union Matrix Baseline}

\subsubsection{原理}

IVF（Inverted File）先通过聚类把 base 向量划分到 $nlist$ 个倒排簇。查询时，每条 query 只访问与其最接近的 $nprobe$ 个簇。在 GPU batch 场景中，batch 内不同 query 的 $nprobe$ 个簇通常不完全相同。指导书指出，这会导致矩阵乘法中出现浪费。

Cluster-Union baseline 按照指导书中的 IVF 矩阵思路实现：对当前 batch 内所有 query 的候选簇取并集 $\mathcal{U}$，然后对每个簇 $c\in\mathcal{U}$，将簇内向量写成矩阵 $L_c$，计算 $L_c Q_b^\top$。如果某条 query 并没有选择簇 $c$，该 query 在此簇上的得分会被丢弃，这部分就是无效计算。实验用
\[
  \rho=\frac{\text{computed pairs}}{\text{useful pairs}}
\]
衡量浪费比。

\subsubsection{伪代码}

\begin{breakablealgorithm}
\caption{GPU IVF Cluster-Union Matrix Baseline}
\begin{algorithmic}[1]
\Require IVF 倒排簇 $\{L_c\}$，centroid 集合 $C$，query batch $Q_b$，$nprobe$，$k$
\Ensure 每条 query 的近似 Top-$k$
\For{每条 query $q_t\in Q_b$}
  \State $P_t\gets$ 与 $q_t$ 最近的 $nprobe$ 个 centroid
\EndFor
\State $\mathcal{U}\gets \bigcup_t P_t$
\For{每个簇 $c\in \mathcal{U}$}
  \State 在 GPU 上计算簇矩阵 $L_c$ 与整个 $Q_b$ 的距离矩阵
  \For{每条 query $q_t$}
    \If{$c\in P_t$}
      \State 将簇 $c$ 中候选及距离加入 $q_t$ 的候选集合
    \EndIf
  \EndFor
\EndFor
\State 对每条 query 的候选集合执行 Top-$k$
\end{algorithmic}
\end{breakablealgorithm}

\subsubsection{复杂度}

IVF 构建阶段使用 $I$ 轮 k-means，近似复杂度为 $\bigO{I\cdot N\cdot nlist\cdot d}$，倒排表空间为 $\bigO{N}$。查询 batch 阶段，若并集簇为 $\mathcal{U}$，则 GPU 实际计算复杂度为：
\[
  \bigO{\left(m\sum_{c\in\mathcal{U}} |L_c|\right)d}.
\]
真正有用的计算量为：
\[
  \bigO{\left(\sum_{t=1}^{m}\sum_{c\in P_t}|L_c|\right)d}.
\]
两者的比值即浪费比 $\rho$。当 batch 内 query 的候选簇重合度较低时，$\rho$ 会显著大于 1，导致矩阵化计算产生大量无效距离项。

\subsubsection{算法分析}

Cluster-Union 保留了规则矩阵乘法形态，簇内向量连续访问，kernel 的内存访问模式较为规整，理论上适合进一步替换为 cuBLAS GEMM 或 shared-memory tiling。该方法也直接对应指导书中 IVF-GPU baseline 的思想，便于观察 query 间并行带来的候选簇不一致问题。其核心缺陷是计算集合由 batch 的簇并集决定，而有效集合由每条 query 的 $nprobe$ 个簇决定；当 batch 较大、$nprobe$ 较大或数据分布导致 query 簇重合度较低时，实际计算量会显著超过必要计算量，端到端性能不一定优于精确 Flat baseline。

\subsection{GPU IVF Compact Pair Optimization}

\subsubsection{原理}

IVF Compact 与 Cluster-Union 使用同样的 IVF 索引和同样的 $nlist/nprobe$ 候选策略，但改变 GPU 任务组织方式。主机端先为 batch 内每条 query 收集其实际要访问的候选向量，然后将所有有效的 $(query,candidate)$ 对压平成一维数组：
\[
  \{(t,i)\mid i\in \bigcup_{c\in P_t} L_c\}.
\]
GPU kernel 每个线程只处理一个有效 pair，通过 \texttt{candidate\_ids} 和 \texttt{query\_ids} 两个数组定位 base 向量与 query 向量。这样避免了对未被某条 query 选择的簇做无效打分。

\subsubsection{伪代码}

\begin{breakablealgorithm}
\caption{GPU IVF Compact Pair Optimization}
\begin{algorithmic}[1]
\Require IVF 倒排簇 $\{L_c\}$，centroid 集合 $C$，query batch $Q_b$，$nprobe$，$k$
\Ensure 每条 query 的近似 Top-$k$
\State 初始化数组 \texttt{candidate\_ids}、\texttt{query\_ids}、\texttt{offsets}
\For{每条 query $q_t\in Q_b$}
  \State $P_t\gets$ 与 $q_t$ 最近的 $nprobe$ 个 centroid
  \For{每个簇 $c\in P_t$}
    \For{每个候选 $i\in L_c$}
      \State 追加 $i$ 到 \texttt{candidate\_ids}，追加 $t$ 到 \texttt{query\_ids}
    \EndFor
  \EndFor
  \State 记录 $q_t$ 的候选区间到 \texttt{offsets}
\EndFor
\State 在 GPU 上每个线程计算一个有效 pair 的距离
\For{每条 query $q_t$}
  \State 使用 \texttt{offsets} 切出其候选距离并执行 Top-$k$
\EndFor
\end{algorithmic}
\end{breakablealgorithm}

\subsubsection{复杂度}

构建复杂度与 Cluster-Union 相同。查询 batch 的 GPU 打分复杂度为：
\[
  \bigO{\left(\sum_{t=1}^{m}\sum_{c\in P_t}|L_c|\right)d}.
\]
空间复杂度为有效 pair 数对应的 \texttt{candidate\_ids}、\texttt{query\_ids} 和 distance 数组。相比 Cluster-Union，Compact 的理论节省比例接近其浪费比 $\rho$，但需要额外维护 pair 索引数组，并引入对 base 向量与 query 向量的间接寻址。

\subsubsection{算法分析}

Compact 的核心思想是把 IVF 查询中的“按簇矩阵化”改为“按有效 pair 稀疏化”。它牺牲了部分矩阵乘法的规整性，换取对无效距离项的彻底剔除，更适合 batch 内 query 候选簇差异较大的场景。该算法的访存连续性弱于 dense GEMM：base 向量通过候选 id 间接读取，query 通过 query id 间接读取，因此单个距离项的访存效率并非最优；但在本实验规模下，减少无效计算和结果传输带来的收益明显大于间接访问开销，是延迟与召回折中最优的 GPU 方案。

从召回率、平均延迟、候选规模和浪费比四个维度看，三类算法体现出不同的性能边界。GPU Flat Batch 是精确检索，Recall@10 接近 1，且在 2000 到 4000 条 query 的规模变化中平均延迟基本稳定，说明 batch 化确实能够充分摊薄 kernel launch 开销并维持较高 GPU 吞吐。然而该算法对每条 query 均访问全部 100000 个 base 向量，候选规模和距离矩阵传输量固定为全库规模，因此它更适合作为精确性能基线，而不是低延迟 ANN 方案。

IVF Cluster-Union 保持了接近矩阵乘法的规则计算结构，但实验结果表明，规则性并不必然带来端到端最优性能。以 $nlist=64,nprobe=8$ 为例，其 Recall@10 与 Compact 方法同为 0.968000，但平均延迟为 377.067 us/query，接近 Flat Batch 的 379.778 us/query。原因在于 batch 内 query 的候选簇并不一致，簇并集计算引入了浪费比 $\rho=5.456155$ 的额外距离项。这说明在 IVF-GPU 中，候选簇一致性是决定矩阵化 baseline 是否有效的关键条件。

IVF Compact 的实验结果构成了本实验中更优的召回--延迟折中。仍以 $nlist=64,nprobe=8$ 为例，它在 2000 条 query 上保持 Recall@10=0.968000，同时平均延迟降至 96.130 us/query，相比 Cluster-Union 加速约 $377.067/96.130\approx3.92$ 倍，相比 Flat Batch 加速约 $379.778/96.130\approx3.95$ 倍。该结果说明，当 IVF 的候选集合天然稀疏且 query 间簇重合度不足时，将任务从“簇矩阵 $\times$ query batch”改写为有效 pair 计算，可以显著降低无效算术、设备到主机传输和主机侧选择压力。

参数层面，$nprobe$ 是最直接的精度--效率调节量。$nlist=64$ 时，$nprobe$ 从 8 增加到 16，Compact 的 Recall@10 从 0.968000 提高到 0.991550，但候选数从 16218.9 增至 29141.9，平均延迟也从 96.130 us/query 增至 180.781 us/query。$nlist$ 的作用更复杂：增大 $nlist$ 会缩小单簇规模并减少候选数，但如果 $nprobe$ 不同步增大，候选覆盖范围下降，召回率可能降低。因此 IVF 参数调优不能只追求更小候选数，而应结合目标 Recall、候选簇覆盖率和 GPU 批处理开销共同确定。

从瓶颈来源看，当前实现仍将 Top-$k$ 选择放在主机侧，GPU 主要承担距离打分。这使得 Flat Batch 受到完整距离矩阵回传限制，Compact 受到候选 id 构造、候选距离回传和主机堆选择限制。若继续优化，可将 per-query Top-$k$ 移至 GPU 端，减少 D2H 数据量；对 Flat Batch 可进一步使用 cuBLAS GEMM 或 shared-memory tiling；对 IVF Compact 可研究候选 pair 的按 query 分组压缩、GPU 端分段 Top-$k$ 和 pinned memory/stream 重叠传输，以进一步降低端到端延迟。

\subsection{GPU Flat Batch Profiling 分析}

Flat Batch 对应的核心 kernel 为 \texttt{flat\_score\_kernel}。在 quick profiling 中，该 kernel 共启动 32 次，Nsight Systems 统计的 GPU kernel 总时间为 411.290 ms，平均每次 launch 约 12.853 ms。该 kernel 的单次任务规模较大：以 batch size 64 为例，一个 launch 需要计算 $64\times 100000$ 个 query--base 距离项，表~\ref{tab:profiling-ncu} 中对应的 grid size 为 25000、线程数为 6400000。

Nsight Compute 显示 \texttt{flat\_score\_kernel} 的内存吞吐率达到 97.64\%，Achieved Occupancy 为 83.40\%，而 SM 计算吞吐率约为 12.03\%。这说明 Flat Batch 的瓶颈并不主要来自浮点乘加能力不足，而是来自全库向量读取、距离矩阵写回以及后续 D2H 传输。结合算法结构看，每条 query 都必须访问全部 100000 个 base 向量，并生成完整距离矩阵，因此该方法虽然规则、负载均衡且召回率最高，但其端到端延迟天然受内存带宽和结果回传约束。

\subsection{GPU IVF Cluster-Union Profiling 分析}

Cluster-Union 对应的核心 kernel 为 \texttt{cluster\_score\_kernel}。该 kernel 在 quick profiling 中启动 6364 次，单次平均只有 51.775 us，但累计 kernel 时间达到 329.498 ms。与 Flat Batch 相比，Cluster-Union 的单个 kernel 更小，但 launch 次数远高于 Flat Batch；这说明其主要性能问题不是单次距离计算过慢，而是 batch 内簇并集拆分后产生了大量细粒度 kernel 和同步事件。

从 Nsight Compute 指标看，\texttt{cluster\_score\_kernel} 的内存吞吐率为 92.49\%，Achieved Occupancy 为 76.86\%。虽然簇内 base 向量访问相对规整，但由于每个 batch 内 query 选择的 IVF 簇并不完全一致，Cluster-Union 需要对簇并集内的向量与整个 query batch 做矩阵化计算，最终产生浪费比 $\rho=5.456155$ 的无效距离项。profiling 结果与实验结果相互印证：该方法保留了矩阵计算的规整形式，却被簇并集导致的无效计算、频繁 launch 和 D2H 回传抵消了收益。

\subsection{GPU IVF Compact Profiling 分析}

Compact 对应的核心 kernel 为 \texttt{indexed\_score\_kernel}。该 kernel 在 quick profiling 中启动 63 次，Nsight Systems 统计的总 kernel 时间为 54.446 ms，平均每次 launch 约 864.226 us，明显低于 Flat Batch 和 Cluster-Union 的总 kernel 时间。该结果说明，把 IVF 查询改写为有效 $(query,candidate)$ pair 后，GPU 实际执行的距离项规模被显著压缩。

Nsight Compute 显示 \texttt{indexed\_score\_kernel} 的 Achieved Occupancy 达到 93.98\%，高于 Flat Batch 和 Cluster-Union；但其内存吞吐率为 85.67\%，低于 Flat Batch。这一现象符合 Compact 的算法特征：candidate id 和 query id 的间接寻址降低了访存规整性，但它剔除了无效候选簇计算，因此总体 kernel 时间更低。换言之，Compact 不是通过单个距离项更快取胜，而是通过减少实际距离项数量和减少 D2H 数据规模获得端到端优势。

\section{结论}

本实验按照 GPU 编程指导书中 ANN 选题要求，完成了矩阵乘法方向的 batch baseline、IVF 方向的簇矩阵 baseline，以及针对 IVF batch 浪费问题的 compact pair 优化。所有主函数、算法函数、索引构建、参数扫描和 CSV 写出均为 C++ 实现，正式实验均从 2000 条 query 起。实验表明，GPU 对 ANN 距离计算的加速必须依赖 query batch；单纯保持矩阵形式并不一定最优，尤其在 IVF 中，batch 内候选簇差异会带来显著无效计算。通过压缩有效 $(query,candidate)$ 对，GPU IVF Compact 在保持较高召回的同时显著降低端到端延迟，是当前实验中最有效的 GPU 优化方案。
