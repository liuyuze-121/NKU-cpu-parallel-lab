\section{问题描述}

近似最近邻搜索（ANNS）在大规模向量检索中面临严重的计算瓶颈。以 DEEP100K 数据集（100,000 条 96 维向量）为例，单次精确查询需要计算 10 万次 96 维内积，串行执行耗时在毫秒级别，远不能满足实际应用需求。

本实验使用 \textbf{pthread} 和 \textbf{OpenMP} 两种多线程编程范式，对 ANNS 的查询阶段进行并行化。核心问题归结为：\textbf{如何将大规模的距离计算任务合理划分给多个线程，并在结果正确的前提下最大化加速比}。

\section{算法设计}

\subsection{Flat-SIMD}

\subsubsection{算法原理}

Flat-SIMD 是 ANNS 中最基础的检索方式——对基向量集合进行全量遍历，用 SIMD 指令加速单次距离计算。由于 Flat 不引入任何索引结构，Recall@K 恒为 1.0（精确结果），因此多线程并行不会损失精度，加速比的唯一限制来自并行效率和硬件资源。

多线程并行的核心思想是\textbf{数据并行（Data Parallelism）}：将 n 条基向量的距离计算任务均匀划分给 T 个线程，每个线程在独立的连续内存区域内执行 SIMD 内积运算、维护局部 top-k 堆，最后由主线程进行 T 路归并得到全局 top-k。由于各线程间的计算完全独立（仅读共享数据、写私有堆），该算法属于\textbf{易并行（Embarrassingly Parallel）}问题，理论加速比接近 T。

\subsubsection{pthread 实现}

\textbf{并行策略：} Base 向量划分 —— 将 n 条基向量按块均匀分配给各线程，每线程独立完成分配范围内的全量距离计算与局部 top-k 维护。

\textbf{伪代码：}

\begin{breakablealgorithm}
\caption{pthread\_flat\_search}
\begin{algorithmic}[1]
\Require base[n][d], query[d], k, num\_threads
\Ensure top-k results (max-heap of $<$dist, index$>$)
\State chunk\_size = n / num\_threads
\State 初始化全局 barrier、T 个局部堆 local\_heaps[T]，每个容量为 k
\For{t = 0 to num\_threads-1}
\State thread\_args[t] = \{base, query, t*chunk\_size, (t+1)*chunk\_size, d, k, \&local\_heaps[t], \&barrier\}
\State pthread\_create(\&threads[t], thread\_worker, \&thread\_args[t])
\EndFor
\State pthread\_barrier\_wait(barrier)
\State global\_heap = merge\_k\_way(local\_heaps[0..T-1], k)
\State \Return global\_heap

\Function{thread\_worker}{args}
\State 初始化空的小顶堆 local\_heap (容量 k)
\For{i = args.start to args.end-1}
\State ip = inner\_product\_neon(args.query, args.base + i*d, args.d)
\If{local\_heap.size < k}
\State local\_heap.push(\{ip, i\})
\ElsIf{ip > local\_heap.top().dist}
\State local\_heap.pop()
\State local\_heap.push(\{ip, i\})
\EndIf
\EndFor
\State 将 local\_heap 写入 args.result
\State pthread\_barrier\_wait(args.barrier)
\EndFunction
\end{algorithmic}
\end{breakablealgorithm}

\textbf{复杂度分析：}

\begin{itemize}
\item \textbf{时间复杂度：} 每个线程计算 n/T 次 NEON 内积，总计 O(n·d/T)。结果归并 O(T·k·log(T·k))，在 T ≤ 16 时远小于距离计算开销。
\item \textbf{空间复杂度：} 每线程存储大小为 k 的局部堆，总计 O(T·k)。基向量为只读共享数据，无需额外副本。
\item \textbf{加速比理论上界：} 各线程计算完全独立，无临界区竞争，理论加速比接近 S(T) = T。实际主要受限于内存带宽和 barrier 同步开销。
\end{itemize}

\textbf{深入分析：} Flat-SIMD 作为易并行问题，在本次 pthread 实测中仍然呈现出接近线性的前半段扩展性，但在 8 线程附近达到最优后开始受平台资源限制：

\begin{enumerate}
\item \textbf{8 线程达到最佳时延：} 平均查询时延从 1 线程的 6567.72\,$\mu$s 降到 8 线程的 2040.90\,$\mu$s，获得 3.22× 加速比。
\item \textbf{4 线程已有较高效率：} 4 线程时延 2246.42\,$\mu$s，加速比 2.92×，效率约 73\%，说明基于向量块的静态划分在中等线程数下负载很均衡。
\item \textbf{16 线程略有回退：} 16 线程平均时延反弹到 2284.98\,$\mu$s，表明继续增加线程后，线程创建/合并以及共享内存带宽竞争开始压过额外并行收益。
\end{enumerate}

\subsubsection{OpenMP 实现}

\textbf{并行策略：} Base 向量划分 —— 使用 \texttt{\#pragma omp parallel for} 自动将循环迭代分布到线程，编译器自动处理任务划分、线程创建和同步。

\textbf{伪代码：}

\begin{breakablealgorithm}
\caption{omp\_flat\_search}
\begin{algorithmic}[1]
\Require base[n][d], query[d], k
\Ensure top-k results
\State T = omp\_get\_max\_threads()
\State 分配 T 个局部小顶堆 local\_heaps[T]，每个容量为 k
\State \textbf{\#pragma omp parallel}
\State[1] tid = omp\_get\_thread\_num()
\State[1] 清空 local\_heaps[tid]
\State[1] \textbf{\#pragma omp for schedule(dynamic)}
\State[1] \For{i = 0 to n-1}
\State[2] ip = inner\_product\_neon(query, base + i*d, d)
\State[2] heap = \&local\_heaps[tid]
\State[2] \If{heap.size < k}
\State[3] heap.push(\{ip, i\})
\State[2] \ElsIf{ip > heap.top().dist}
\State[3] heap.pop(); heap.push(\{ip, i\})
\State[2] \EndIf
\State[1] \EndFor
\State global\_heap = merge\_k\_way(local\_heaps[0..T-1], k)
\State \Return global\_heap
\end{algorithmic}
\end{breakablealgorithm}

\textbf{复杂度分析：} 渐近复杂度与 pthread 相同。主要差异在于 OpenMP 维护线程池，免去 \texttt{pthread\_create}/\texttt{pthread\_join} 开销；\texttt{schedule(dynamic)} 在 Flat 均匀计算量场景下引入了不必要的分发锁，改为 \texttt{schedule(static)} 可消除此开销。

\subsection{PQ-SIMD}

\subsubsection{算法原理}

乘积量化（Product Quantization, PQ）是向量压缩领域最具代表性的有损编码技术。其核心思想是将高维向量空间分解为多个低维子空间的笛卡尔积，在每个子空间内独立进行 KMeans 聚类，将原始浮点向量替换为聚类中心索引序列，从而将存储和计算代价降低 1~2 个数量级。

以本实验 DEEP100K 数据集（d=96）为例，取 M=8 个子空间，每个子空间维度 dsub = 96/8 = 12，每子空间 ksub=256 个聚类中心。编码后每条向量从 96×4 = 384 字节压缩为 8×1 = 8 字节（uint8 索引），压缩比达 48:1。

查询采用\textbf{非对称距离计算（ADC）}：对查询向量 q 不做量化（避免引入查询端量化误差），而是预计算 q 的每个子向量到对应子空间全部 ksub 个聚类中心的距离，形成 M×ksub 的查找表（LUT）。随后对每条编码向量，仅需 M 次查表和累加即可估算出与 q 的近似距离。

\textbf{查询流程的瓶颈转移：} PQ 将距离计算从 compute-bound 的浮点乘加转变为 memory-bound 的查表累加。单次查询需随机访问 codes 数组中 n×M 个 uint8 索引，再用这些索引随机访问 LUT。双重的随机内存访问模式使得 cache miss 率显著升高，多线程环境下的内存带宽竞争成为决定加速比上限的关键因素。

\subsubsection{pthread 实现}

\textbf{并行策略：} 对 LUT 构建阶段按子空间划分线程，对查表累加阶段按 Base 向量分块。

\textbf{伪代码：}

\begin{breakablealgorithm}
\caption{pq\_search\_pthread}
\begin{algorithmic}[1]
\Require codes[n][M], centroids[M][ksub][dsub], norms[n], query[d], k, p, num\_threads
\Ensure top-k results
\State chunk\_m = M / num\_threads
\State lut[M][ksub]
\State 创建线程，每个线程 t 处理子空间 [t*chunk\_m, (t+1)*chunk\_m]
\Function{build\_lut\_thread}{t}
\For{m = t*chunk\_m to (t+1)*chunk\_m-1}
\State query\_sub = query + m*dsub
\For{ki = 0 to ksub-1}
\State centroid = centroids + m*ksub*dsub + ki*dsub
\State lut[m][ki] = l2\_distance\_neon(query\_sub, centroid, dsub)
\EndFor
\EndFor
\State pthread\_barrier\_wait(\&phase1\_barrier)
\EndFunction

\State q\_norm = dot\_product\_neon(query, query, d)
\State chunk\_n = n / num\_threads
\State 分配 local\_candidates[T]，每个容量为 p（小顶堆）

\Function{scan\_thread}{t}
\For{i = t*chunk\_n to (t+1)*chunk\_n-1}
\State dist = 0
\For{m = 0 to M-1}
\State dist += lut[m][codes[i*M + m]]
\EndFor
\State ip = (q\_norm + norms[i] - dist) / 2
\State 维护 local\_candidates[t] 为大小为 p 的小顶堆
\EndFor
\State pthread\_barrier\_wait(\&phase2\_barrier)
\EndFunction

\State 将 T 个 local\_candidates 中的 p*T 个候选合并，取前 k 个
\State \Return global\_top\_k
\end{algorithmic}
\end{breakablealgorithm}

\textbf{复杂度分析：}

\begin{itemize}
\item \textbf{LUT 构建：} O(M·ksub·dsub / T)，在 M=8 时计算量约 Flat 的 0.1\%，并行收益有限。
\item \textbf{查表累加：} O(n·M / T)。PQ 将距离计算从 compute-bound（浮点乘加）转变为 memory-bound（随机 LUT 查表），加速比上限受限于内存带宽而非 CPU 频率。
\item \textbf{空间复杂度：} O(n·M + M·ksub·dsub)。p 参数增大时堆维护开销从 O(log k) 增至 O(log p)。
\end{itemize}

\textbf{深入分析：} 按参数组合实际测试后，pthread PQ 的规律与理论预期一致：

\begin{enumerate}
\item \textbf{最优线程数稳定在 4 附近：} 无论是 M=8 还是 M=16，大多数配置在 4 线程达到最低时延，例如 M=8,p=1000 时为 1628.70\,$\mu$s，M=16,p=1000 时为 2074.47\,$\mu$s。
\item \textbf{p 增大主要提升召回率，但显著增加时延：} 以 M=8 为例，p 从 1000 增至 5000，Recall@10 从 0.994501 升至 0.99985，而 1 线程时延从 2617.92\,$\mu$s 增至 5775.43\,$\mu$s。
\item \textbf{M=16 进一步提升精度：} 在 p=2000 时，M=16 已达到 0.99995 的平均召回率，但最优 4 线程时延仍为 3167.08\,$\mu$s，明显慢于 M=8,p=1000 的低时延配置。
\end{enumerate}

\subsubsection{OpenMP 实现}

\textbf{并行策略：} LUT 构建阶段使用 \texttt{schedule(static)} 按子空间均分，查表累加阶段使用 \texttt{schedule(dynamic, chunk\_size)} 按基向量范围动态调度以缓解内存带宽竞争导致的计算时间不均。

\textbf{实测分析：} OpenMP PQ 在本地环境下没有表现出 pthread 那样稳定的收益，反而暴露出实现层面的额外开销：

\begin{enumerate}
\item \textbf{4 线程不一定更快：} 例如 M=8,p=1000 时，1 线程时延为 2335.91\,$\mu$s，但 4 线程上升到 4708.48\,$\mu$s，说明并行化后的局部候选维护与合并成本超过了收益。
\item \textbf{M=16 更适合作为 OpenMP 版本的代表性配置：} M=16,p=1000,4 线程达到 Recall@10=0.99995、时延 1772.34\,$\mu$s，既保持高召回，也优于 Flat 的 4 线程结果。
\item \textbf{p 增大后时延近似单调上升：} M=8 时 p 从 1000 提高到 5000，时延由 4708.48\,$\mu$s 增至 4757.53\,$\mu$s，而召回率才从 0.993701 升至 0.999850，性价比不高。
\end{enumerate}

\subsection{IVF-SIMD}

\subsubsection{算法原理}

倒排文件（Inverted File, IVF）索引借鉴了信息检索中倒排索引的思想，通过离线聚类将基向量空间划分为 nlist 个 Voronoi 区域。在线查询时，仅需搜索距离查询向量最近的 nprobe 个区域，从而将候选集从 n 缩减至约 nprobe × n/nlist。

IVF 的查询过程分为\textbf{粗排（Coarse Search）}和\textbf{精排（Fine Search）}两个阶段：

\begin{enumerate}
\item \textbf{粗排：} 计算查询向量 q 到 nlist 个聚类中心的距离，用 partial sort 选取距离最近的 nprobe 个簇。计算量为 O(nlist×d)，通常 nlist ≪ n。
\item \textbf{精排：} 遍历选中的 nprobe 个簇的倒排链表，对其中每个基向量 x 计算 SIMD 内积，维护全局 top-k。
\end{enumerate}

\textbf{多线程并行挑战：} KMeans 聚类产生的倒排链表长度不均匀是固有特性。更好的策略是将所有候选向量展平为一个连续数组，然后按向量粒度的 Base 划分并行——这与 Flat 的并行模式完全一致，但候选集规模远小于 n。

\subsection{IVF-PQ-SIMD}

\subsubsection{算法原理}

IVF-PQ 是 IVF 索引结构与 PQ 编码技术的组合：IVF 负责缩小搜索范围（粗排剪枝），PQ 负责降低单条距离计算代价（ADC 查表累加）。两者形成\textbf{两级近似}。

\textbf{查询流程：}
\begin{enumerate}
\item IVF 粗排选择簇
\item 构建 PQ LUT
\item 对候选向量的 PQ code 进行查表累加估算距离
\item 根据估算距离选取 top-p 候选，用原始浮点向量重排得到精确 top-k
\end{enumerate}

\item \textbf{低 nprobe 时延较低：} nlist=100,M=8,nprobe=1,p=1000,1 线程时延为 470.04\,$\mu$s，Recall@10=0.635700。
\item \textbf{提高 nprobe 后精度上升但仍弱于 IVF：} nprobe=4 时 Recall@10 提升到 0.904653，时延升至 762.69\,$\mu$s，仍落后于 OpenMP IVF 在相近延迟区间的表现。
\item \textbf{因此未作为最终提交候选：} 在当前 DEEP100K 场景下，OpenMP IVF 的召回-时延权衡更直接、也更稳定。
\end{enumerate}

\subsection{HNSW 图索引}

\subsubsection{算法原理}

HNSW（Hierarchical Navigable Small World）是当前工业界综合性能最优的 ANNS 索引结构之一。它构建了一个多层近邻图，其中每层是一个可导航小世界图（NSW），不同层间通过指数衰减的概率分布建立连接。

\textbf{层级结构设计：} 每个节点被随机分配一个整数层级 l ∈ [0, L]，分配概率服从指数分布。层级越高节点越稀疏。查询时从顶层入口点开始，在每层执行贪心搜索找到局部最近点，然后下降到下一层以该点为起点继续搜索。

\textbf{HNSW 并行化的核心困境：} 图搜索具有天然的\textbf{顺序依赖性}——每一步扩展哪个节点取决于上一步的计算结果。目前可行的并行策略集中于 Query 级并行（不同线程处理不同查询）。

\subsubsection{pthread 实现}

\textbf{并行策略：} 构图阶段直接调用 hnswlib::HierarchicalNSW 串行 addPoint（hnswlib 内部已处理图结构正确性）；批量查询阶段采用 Query 级并行，将 N 条 query 按 chunk 划分给 T 个 pthread，每个线程独立执行 hnswlib::searchKnn。

\textbf{伪代码：}

\begin{breakablealgorithm}
\caption{hnsw\_pthread\_batch\_search}
\begin{algorithmic}[1]
\Require base[n][d], queries[N][d], k, num\_threads, hnswlib::InnerProductSpace space, hnswlib::HierarchicalNSW$<$float$>$ index (已 build)
\Ensure top-k results for each query
\State space.reset(new InnerProductSpace(d))
\State index.reset(new HierarchicalNSW$<$float$>$(space.get(), n, M, efConstruction))
\State index.setEf(ef)
\For{i = 0 to n-1}
\State index.addPoint(base + i*d, i)  \Comment{构图阶段：串行 addPoint}
\EndFor
\Function{search\_single}{q}
\State pq = index.searchKnn(q, k)
\State res = empty max-heap
\While{!pq.empty()}
\State (dist, id) = pq.pop()
\State res.push(\{dist, id\})
\EndWhile
\State \Return res
\EndFunction
\State chunk = N / num\_threads
\State 创建 threads[0..T-1] 与 args[0..T-1]
\For{t = 0 to num\_threads-1}
\State args[t] = \{this, queries, k, results, t*chunk, (t+1)*chunk\}
\State pthread\_create(\&threads[t], batch\_worker, \&args[t])
\EndFor
\For{t = 0 to num\_threads-1}
\State pthread\_join(threads[t], NULL)
\EndFor
\State \Return results[0..N-1]
\Function{batch\_worker}{arg}
\For{i = arg.start to arg.end-1}
\State results[i] = search\_single(queries[i])
\EndFor
\State \Return NULL
\EndFunction
\end{algorithmic}
\end{breakablealgorithm}

\textbf{复杂度分析：}
\begin{itemize}
\item \textbf{构图：} O(n·log(n))，hnswlib 内部完成，多线程加速主要在 build 的 addPoint 并行上。
\item \textbf{单查询：} O(log(n)·ef·d)，由 hnswlib::searchKnn 实现。
\item \textbf{批量查询并行：} N 个 query 总耗时 T = $\sum$per-query 耗时 / T 路并行近似为 T/N，N 越大加速越接近 T。
\end{itemize}

\textbf{深入分析：} pthread HNSW 选取了 M \in \{16,32\}、efConstruction=150、ef \in \{10,20,50,100\}、线程数 \in \{1,4\} 的代表性组合进行测试。详细的 16 组 Recall@10 与时延见第 \ref{sec:hnsw-perf} 节 ``HNSW 图索引性能分析''，整体趋势表明：

\begin{enumerate}
\item \textbf{ef 是主要精度控制参数：} ef 增大时召回率上升、时延同步上升。
\item \textbf{Query 级并行非常有效：} 对 HNSW 这类单查询强顺序依赖算法，跨查询并行比在单查询内部并行更自然。
\item \textbf{若追求提交的稳定性与可复现性，IVF 更合适：} HNSW 在本实现中还包含较重的图构建阶段，测试与正式提交时总耗时更敏感，因此本次未将其作为最终保留配置。
\end{enumerate}

\begin{breakablealgorithm}

\end{breakablealgorithm}

\textbf{复杂度分析：} 与 pthread 相同。OpenMP 通过动态调度避免某条 query 因 ef 大、图路径长而被串行调度阻塞，但单 query 内部仍由 hnswlib 顺序扩展。

\textbf{实测分析：} OpenMP HNSW 基于 hnswlib::HierarchicalNSW 基础图索引实现，构图与查询均由经工业验证的基础图索引完成，多线程 OpenMP 仅用于 query 级的批量搜索并行，本地测试稳定可运行。详细的 M \in \{16,32\}、efConstruction=150、ef \in \{10,20,50,100\}、线程数 \in \{1,4\} 共 16 组配置下的 Recall@10 与时延请见第 \ref{sec:hnsw-perf} 节 ``HNSW 图索引性能分析''。综合而言，OpenMP HNSW 在 M=32,ef=100,4T 下能达到 Recall@10=0.995601、Latency=178\,$\mu$s，是高召回 + 极低时延的潜在替代方案；但由于本次实验范围内 HNSW 仍作为参考配置，真实提交仍以 OpenMP IVF 为准。

\section{总结与收获}

\subsection{主要结论}

\begin{enumerate}
\item pthread 版本五类算法均已接入统一主程序入口，可通过轻量参数切换运行。
\item 从 pthread 最终真实提交结果看，\textbf{pthread IVF-SIMD（nlist=256,nprobe=32,threads=4）} 的 Recall@10=0.990251，平均延迟为 1290.95 $\mu$s。
\item 从 OpenMP 真实提交结果看，\textbf{OpenMP IVF-SIMD（nlist=256,nprobe=32,threads=4）} 是最终提交版本：Recall@10=0.990501，平均延迟 928.419 $\mu$s。
\item 将 omp/hnsw\_omp.h 与 pthread/hnsw\_pthread.h 改为直接基于 hnswlib::HierarchicalNSW 基础图索引后，HNSW 在两种线程模型下都通过基础运行校验：pthread M=32,ef=100,4T 达到 Recall@10=0.995601、Latency=202 $\mu$s；OpenMP M=32,ef=100,4T 达到 Recall@10=0.995601、Latency=178 $\mu$s，在 4 线程下相对 OpenMP IVF 真实提交同时具备更高召回与约 5$\times$ 更低时延的潜力。
\end{enumerate}

\subsection{实验收获}

通过本实验，深入理解了：
\begin{enumerate}
\item ANNS 算法在 pthread 与 OpenMP 两种线程模型下的统一调度方式
\item 线程级数据并行与图查询级并行的差异
\item IVF 系列在召回率与时延之间的可调权衡
\item 在既定主程序框架下尽量少改动完成多算法接入的方法
\item 借助成熟的 hnswlib 基础图索引实现 HNSW：使用 hnswlib::InnerProductSpace 与 HierarchicalNSW 作为构图与查询的底层组件，可以专注于 ``Query 级并行'' 这一层并行化设计，将图结构正确性交给工业级实现。
\end{enumerate}
